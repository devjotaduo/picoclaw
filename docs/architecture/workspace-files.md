# Workspace files reference

This is the canonical layout of files inside a Picoclaw SaaS *Workspace* — the admin-managed
directory that auto-provisioning copies into each new tenant volume. It complements
[workspaces.md](workspaces.md) (which covers the DB row, mounts, and lifecycle).

## Filesystem layout

```
<WorkspaceDir>/<slug>/
├── home/                          ← bind-mounted into tenant container as /root/.picoclaw
│   ├── config.json                ← REQUIRED — runtime config + placeholders
│   ├── .security.yml              ← recommended — permissions / tool allowlist
│   ├── auth.json                  ← recommended — OAuth credentials per provider
│   └── workspace/
│       ├── AGENT.md               ← REQUIRED — prompt + frontmatter
│       ├── SOUL.md                ← REQUIRED — identity / brand / tone
│       ├── behavior.json          ← REQUIRED — DM/group/business-hours hard filters
│       ├── agent_config.json      ← optional — round-trip payload for the UI editor
│       ├── agents/<id>/           ← optional — secondary personas
│       │   ├── AGENT.md
│       │   ├── SOUL.md
│       │   └── behavior.json
│       ├── skills/<name>/         ← optional — curated skill packs
│       │   ├── SKILL.md
│       │   └── scripts/*.sh
│       ├── memory/*.md            ← optional — static business facts (FAQ, company info)
│       ├── HEARTBEAT.md           ← optional — heartbeat-mode operator notes
│       ├── IDENTITY.md            ← optional — extended identity
│       └── cron/*.json            ← optional — scheduled agent tasks
├── frontend-src/                  ← optional — React source per workspace (forked from web/frontend/)
└── frontend-dist/                 ← generated by "Compilar frontend" — bind-mounted ro into tenant
```

## What each file does

### Required (tenant won't boot without these)

| File | Role |
|---|---|
| `home/config.json` | `model_list[]`, `channel_list{}`, `agents.defaults`, `gateway`, `isolation`, `tools`, `events`. Contains `${LITELLM_KEY}`, `${LITELLM_URL}`, `${TENANT_ID}` placeholders that the provisioner substitutes per-tenant. |
| `home/workspace/AGENT.md` | Main agent prompt + YAML frontmatter (`name`, `model`, `skills`, `tool_allowlist`). The runtime source-of-truth for the prompt. |
| `home/workspace/SOUL.md` | Identity: name, role, tone, language. Driven into the system prompt at session start. |
| `home/workspace/behavior.json` | Hard switches that channels and the agent loop enforce: `master_enabled`, `respond_in_dm`, `respond_in_groups`, `group_mention_only`, `business_hours`, `pii_masking`, `handoff_keywords`. |

### Recommended

| File | Role |
|---|---|
| `home/.security.yml` | Tool allowlist, isolation enablement, channel allowlist fallback, auth resolution order. Conservative defaults if absent. |
| `home/auth.json` | OAuth credentials per provider (Codex, Claude CLI, GitHub, etc.). Empty `{ "providers": {} }` by default. See **Shared auth** below. |
| `home/workspace/memory/*.md` | Static facts the agent loads each turn (company info, FAQ, authorized channels). |
| `home/workspace/agent_config.json` | Payload that round-trips through the admin UI editor. Not the runtime source of truth — `AGENT.md`/`SOUL.md`/`behavior.json` always win on conflict. |

### Optional (used by specific patterns)

| File / dir | When to use |
|---|---|
| `home/workspace/agents/<id>/` | Multi-agent tenant. The dispatcher routes incoming messages to the right persona via `agents.dispatch.rules` in `config.json`. |
| `home/workspace/skills/<name>/SKILL.md` | Installable skill with frontmatter (`name`, `description`, `language`, `metadata.visible`) and a body that serves as both docs and prompt. Optional `scripts/*.sh` for shell execution. |
| `home/workspace/cron/*.json` | Scheduled agent invocations. |
| `home/workspace/HEARTBEAT.md` | Operator notes for tenants running in heartbeat mode (periodic activation). |
| `home/workspace/IDENTITY.md` | Extended identity that goes beyond `SOUL.md`. |

### NEVER in `home/` (runtime state, provisioner-owned, secrets)

These get created by the launcher / provisioner at runtime and must not appear in the workspace template:

- `launcher-auth.db` (a.k.a. dashboardauth.db) — provisioner generates with the dashboard password
- `launcher_policy.json` — provisioner writes from the workspace's `role_policy_json` DB column
- `litellm.key` — provisioner generates the LiteLLM virtual key
- `home/workspace/sessions/` — agent conversation history
- `home/workspace/whatsapp/store.db` — whatsmeow's session store
- `home/state/state.json` — last-channel / last-chat tracker
- `home/runtime-user-env/` — `$HOME`/`$TEMP` redirected for sandboxed subprocesses
- `home/.picoclaw.pid` — launcher PID file
- `home/logs/`, `home/backups/` — launcher's own log + backup dirs

The admin file editor (`adm.<base>/workspaces/{id}/files` and `adm.<base>/tenants/{id}/files`) filters
these paths out of the tree AND blocks writes to them — defence in depth.

## Placeholder substitution

The provisioner runs `SubstituteConfigPlaceholders` on `home/config.json` (only) right after copying
the workspace into the tenant volume. Tokens recognized:

| Token | Replaced with |
|---|---|
| `${LITELLM_KEY}` | The newly-generated per-tenant LiteLLM virtual key |
| `${LITELLM_URL}` | `http://litellm:4000/v1` (from `LITELLM_URL` env on the controlplane) |
| `${TENANT_ID}` | The tenant's slug-suffixed ID (e.g. `onboarding-eb7586`) |

Tokens NOT in this list pass through untouched. The provisioner does NOT substitute placeholders
anywhere else in the workspace (markdown, behavior.json, skill scripts) — those stay literal.

## Authority hierarchy

When fields conflict between files, the launcher resolves in this order:

1. **`AGENT.md` frontmatter** — model, skills, tool_allowlist
2. **`SOUL.md` body** — identity / brand / tone
3. **`behavior.json`** — hard filter switches
4. **`config.json`** — `agents.defaults` for global runtime settings

`agent_config.json` is editor-only metadata and is NEVER consulted at runtime. If you see a mismatch
between e.g. company name in `agent_config.json` vs `SOUL.md`, treat it as data drift in the editor
payload — not a runtime renderer bug.

## Shared OAuth credentials (Codex, Claude CLI, etc.)

By default each tenant boots with an empty `auth.json`. The operator can either:

**(a)** Authenticate per-tenant by `docker exec`-ing into the container and running
`picoclaw auth login <provider>`. Tokens land in `/root/.picoclaw/auth.json` for that tenant only.

**(b)** Authenticate ONCE at the controlplane level by:

1. Generate the auth.json on any picoclaw install (`picoclaw auth login codex`)
2. Copy the resulting `~/.picoclaw/auth.json` onto the controlplane host at
   `/etc/picoclaw/shared-auth.json` (or override the path via
   `PICOCLAW_SHARED_AUTH_PATH` env on the controlplane)
3. Every NEW tenant gets that file copied into its volume at provision time, overriding the empty
   baseline. Existing tenants are unaffected — recreate them (`picoclaw-tenantctl recreate <id>`)
   to pick up fresh tokens.

The copy is a SNAPSHOT — operator edits to `shared-auth.json` after provision don't propagate
automatically. Treat token rotation as a "recreate all tenants" operation.

## Bootstrap → first run

When the controlplane starts with an empty `workspaces` table, `EnsureDefaultWorkspace` runs and:

1. Creates a workspace row `default-business` with `is_default_auto=true`
2. Pre-creates the three subdirs at `<WorkspaceDir>/default-business/{home, frontend-src, frontend-dist}/`
3. Seeds `home/workspace/` from `/srv/picoclaw/workspace/` if that legacy path is bind-mounted ro
4. Extracts the embedded baseline (skip-if-exists per file) to fill in any gaps:
   - `home/.security.yml`
   - `home/auth.json` (empty `{ "providers": {} }`)
   - `home/workspace/AGENT.md`, `SOUL.md`, `behavior.json` (only if step 3 didn't already write them)
5. Writes `home/config.json` with placeholders (only if absent)

The baseline is intentionally generic ("assistente padrão" in pt-br with sane behavior defaults)
so the OSS repo doesn't ship customer content. Operators customize after the fact via the admin UI
or by SSH-editing the workspace on the host before the first auto-provision fires.

## Validation

Workspaces page → "Validação do workspace" panel calls
`GET /api/v1/workspaces/{id}/validate` and surfaces a checklist of every required + recommended
file, marking which are present. A workspace with ANY required file missing will fail auto-
provisioning — fix the gaps before Clara qualifies a lead.

You can also hit the endpoint directly:

```bash
curl https://adm.<base>/api/v1/workspaces/default-business-XXXXXX/validate -H 'cookie: ...'
```

Returns `{ ok: true|false, rows: [...] }`.
