## Achados

### 🔴 BLOQUEANTE — B1: Testes contaminam estado real do workspace

**Gravidade:** Bloqueante para CI/automação
**Descrição:** `state.py` lê/escreve `state/onboarding.json` e `memory/empresa.md` do workspace real (detectando a raiz por heurística AGENT.md). Não há flag `--dry-run` ou variável de ambiente para apontar para um workspace de teste isolado.
**Impacto:** Qualquer execução de teste automatizado contamina o estado de produção do tenant. Este relatório teve que restaurar manualmente 4 arquivos após os testes.
**Correção sugerida:** Adicionar suporte a `PICOCLAW_WORKSPACE_OVERRIDE` env var em `find_workspace_root()`, ou flag `--workspace <path>` no CLI do `state.py`. A skill `onboarding-state/SKILL.md` deve documentar o uso da variável para testes.
**Arquivo:** `skills/onboarding-state/scripts/state.py` linha 207 (`find_workspace_root`)

---

### 🔴 BLOQUEANTE — B2: Sanitização remove tags HTML mas mantém conteúdo interno (inner text)

**Gravidade:** Bloqueante para confiança dos dados em empresa.md
**Descrição:** `sanitize_short_text()` usa `_TAG_LIKE_RE = re.compile(r"<[^>]+>")` que remove apenas as tags `<...>` mas mantém o texto entre elas. `<script>alert(1)</script>Clínica` → `alert(1)Clínica` gravado no campo `Nome:` do empresa.md.
**Impacto:** Nomes de empresas com tags HTML (tipicamente XSS tentado via input do usuário) resultam em lixo nos dados. Em ambiente onde empresa.md é renderizado via template web, pode vazar XSS residual. O comentário no código diz "downstream readers MUST NOT trust state.json as already-safe HTML" mas empresa.md é renderizado em telas.
**Correção sugerida:** Após strip de tags, adicionar strip do conteúdo de `<script>...</script>` e `<style>...</style>` (conteúdo destrutivo). Modelo:
```python
_SCRIPT_CONTENT_RE = re.compile(r"<(script|style)[^>]*>.*?</(script|style)>", re.IGNORECASE | re.DOTALL)
# apply before _TAG_LIKE_RE
cleaned = _SCRIPT_CONTENT_RE.sub("", value)
```
**Arquivo:** `skills/onboarding-state/scripts/state.py` linha 136

### 🟡 MELHORIA — M1: Arquivo `clinica.md` recomenda agentes que não existem no roster

**Gravidade:** Melhoria
**Descrição:** `skills/jotaduo-discovery/references/segments/clinica.md` linhas 52–58 recomenda `agente-recepcionista`, `agente-agendador`, `agente-pos-venda`, `agente-cobranca` como "Time típico". Esses IDs não existem no `agent-catalog.md` nem em `config.json`. O roster real usa `clara`, `luna`, `camila`.
**Impacto:** Sofia pode recomendar agentes fantasmas ao dono, causando confusão. O dono vai perguntar "onde fica o `agente-recepcionista`?" e não vai achar.
**Correção sugerida:** Substituir a seção "Time típico de agentes" em `clinica.md` pelos IDs reais do roster: clara → atendente principal; luna → cobertura noturna; camila → pós-consulta. Aplicar mesmo fix nos demais arquivos de segmento.
**Arquivos:** `skills/jotaduo-discovery/references/segments/clinica.md` (e demais segmentos)

---

### 🟡 MELHORIA — M2: agent-catalog.md não reflete todos os agentes do roster

**Gravidade:** Melhoria
**Descrição:** O `agent-catalog.md` lista 9 agentes mas omite: `pixel`, `doc`, `dev`, `transferencia-humana`, `sofia`, `catarina`. Sofia pode referenciar esses nomes na conversa e o catalog não os explica ao modelo.
**Impacto:** Sofia pode omitir agentes relevantes (ex: `lia` para marketing) por falta de contexto no catálogo.
**Correção sugerida:** Adicionar `pixel`, `doc`, `dev` na seção de agentes especializados. Deixar `sofia`, `catarina`, `transferencia-humana` documentados como "agentes internos — não recomendar ao dono".

---

### 🟢 INFO — M3: state.py `find_workspace_root` falha silenciosamente em paths sem AGENT.md

**Gravidade:** Info
**Descrição:** Se `state.py` for executado de um diretório sem `AGENT.md` na hierarquia E sem `PICOCLAW_HOME` setado, emite `SystemExit("could not find workspace root")` com mensagem razoável. Porém em dev Windows, a heurística `parent.name.lower() == "workspace"` é case-sensitive no `.name` mas não no sistema de arquivos — risco baixo.
**Impacto:** Baixo — apenas ambientes dev Windows afetados.
